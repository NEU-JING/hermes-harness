# 阶段间内部一致性审计规范

> **用户原话引用**："我检查了一下你目前的成果物，前后存在不一致的情况... 先别着急编码，我们先把基础打好，必须确保成果物的前后一致性"
>
> **核心教训**：写一致性保障机制的人，自己写的文档首先必须一致。否则是最讽刺的反例。

---

## 强制执行规则

**推进到下一阶段前，必须先完成本阶段的内部一致性审计。不通过审计，不能继续。**

| 当前阶段 | 审计时机 | 必须通过的审计项 |
|---------|---------|----------------|
| BA 完成 | 推进到 Architect 前 | ✅ Spec 内部一致性审计 |
| Architect 完成 | 推进到 Coder 前 | ✅ Design + Tasks 内部一致性审计 |
| Coder 完成 | 推进到 Reviewer 前 | ✅ 代码与 Spec 一致性审计 |

---

## Spec 内部一致性审计清单（BA → Architect）

执行以下所有检查，全部通过才能推进：

### 1. 术语表述统一性

| 检查项 | 执行命令 | 通过标准 |
|-------|---------|---------|
| 核心术语表述 | `grep -o "三层\|四层" spec.md \| sort \| uniq -c` | 只能出现一个表述（如只能"三层"或只能"四层"） |
| 关键字一致性 | `grep -o "必须\|禁止\|应该\|不应该" spec.md \| head -20` | 同一概念的约束不能前后矛盾 |
| 命名风格统一 | 搜索所有变量/接口/类名的大小写风格 | 不能同时出现 `user_id` 和 `userId` |

### 2. 编号连续性

| 检查项 | 执行命令 | 通过标准 |
|-------|---------|---------|
| Requirement 编号 | `grep "^### Requirement" spec.md \| cat -n` | R1-Rn 必须连续，无重复，无跳跃 |
| 章节编号 | `grep "^## " spec.md \| cat -n` | 1. / 2. / 3. 必须连续 |
| 小节编号 | `grep "^### " spec.md \| cat -n` | 1.1 / 1.2 / 2.1 必须连续 |
| AC 编号 | `grep "^#### AC" spec.md \| cat -n` | AC1-ACn 必须连续 |
| 表格/图片编号 | `grep "表[0-9]\+\|图[0-9]\+\|Table [0-9]\+\|Figure [0-9]\+" spec.md` | 编号连续无重复 |

### 3. 引用完整性

| 检查项 | 通过标准 |
|-------|---------|
| 引用目标存在 | "见 R3" / "参见 2.3 节" → 目标 R3 / 2.3 节必须存在 |
| 引用编号正确 | "见下表 3" → 后面确实有表 3 |
| 术语表覆盖 | 所有专业术语必须先在术语表定义，才能在正文中使用 |

### 4. PRD vs Spec 映射完整性

| 检查项 | 通过标准 |
|-------|---------|
| 功能点完全映射 | PRD 中提到的每个功能点 → Spec 中都有对应的 Requirement |
| 约束不放松 | PRD 中的约束 → Spec 中不能放宽或删除 |
| 目标不漂移 | PRD 中的目标 → Spec 中不能变更范围 |

## Design + Tasks 内部一致性审计清单（Architect → Coder）

### 1. Spec vs Design 一致性

| 检查项 | 通过标准 |
|-------|---------|
| 所有 R 都覆盖 | Spec 中的每个 Requirement → Design 中都有对应的设计方案 |
| 约束不突破 | Spec 中的约束 → Design 中不能突破 |
| 术语一致 | Spec 中定义的术语 → Design 中不能换说法 |

### 2. Design vs Tasks 一致性

| 检查项 | 通过标准 |
|-------|---------|
| 所有设计都有对应 Task | Design 中的每个模块/接口/数据结构 → Tasks 中都有对应的实现任务 |
| Task 顺序与设计依赖一致 | Task 执行顺序必须符合设计的依赖关系 |
| 验收标准清晰 | 每个 Task 都有明确的验收标准，可验证 |

## 审计执行流程（强制执行）

```bash
# 1. 术语表述检查
echo "=== 术语检查 ==="
grep -o "三层\|四层" docs/changes/<id>/spec.md | sort | uniq -c

# 2. 编号连续性检查
echo "=== Requirement 编号 ==="
grep "^### Requirement" docs/changes/<id>/spec.md | cat -n
echo "=== 章节编号 ==="
grep "^## " docs/changes/<id>/spec.md | cat -n

# 3. 引用完整性检查（手动）
# 搜索所有 "见 R" / "参见" / "参考"，验证目标存在

# 4. PRD vs Spec 映射检查（手动）
# 打开 PRD，逐条核对每个功能点在 Spec 中是否有对应 R

# 5. 全部通过后，输出审计通过记录
echo "✅ 内部一致性审计通过" >> docs/changes/<id>/audit-log.md
```

---

## 发现不一致的处理流程

1. **立即停止推进**：不允许进入下一阶段
2. **定位根因**：为什么会出现不一致？是复制粘贴错误？还是理解偏差？
3. **统一修正**：以最新的设计决策为准，全文统一表述
4. **重新审计**：修正后必须重新跑完整的审计清单
5. **记录教训**：把这次不一致的类型和原因记录到 `audit-log.md` 中，避免再犯

---

## 常见不一致类型及预防

| 不一致类型 | 案例 | 预防措施 |
|----------|------|---------|
| 术语表述漂移 | 前面说"三层"，后面又说"四层" | 写文档前先定义术语表，写的时候先看术语表 |
| 编号重复 | 插入新 R 时，后面的编号没改，出现两个 R7 | 用脚本自动编号，或写完后 grep 检查 |
| 前后矛盾 | 前面说"必须支持增量更新"，后面又说"全量覆盖" | 写完后全文搜索"必须"/"禁止"，检查是否矛盾 |
| 引用失效 | "见 3.2 节"但 3.2 节已经被删掉或改名 | 写完后搜索所有引用，验证目标存在 |

## 核心原则（用户强调）

> **不要让用户帮你发现文档不一致。你是写一致性保障机制的人，必须首先确保你自己写的文档是一致的。**
>
> 推进到 Architect 阶段前，BA 必须先自我审计；推进到 Coder 阶段前，Architect 必须先自我审计。
>
> **永远把基础打好，再往下走。**
