# SDD-for-Planning：用 SDD 流程组织改进项

> 适用场景：用户说"安排一下"某个改进清单、调研结论、待办列表等，期望结构化的规划而非随意执行。

---

## 工作流

当用户给出多个改进点并要求"安排一下"时，使用 SDD 流程的 **PO 阶段**进行规划：

```
用户指令: "针对XX对比报告，安排一下改进点3，4，5，7，8"

↓

1. 初始化 Change
   → 创建 docs/changes/{change-id}/ 目录
   → 创建 .sdd-state.json（incremental_mode: true）
   → 按改进点间的逻辑依赖划分 Phase

2. 产出 PRD
   → 每个改进点一个小节：问题 → 目标 → 关键思路 → 对比参考
   → 定义 Phase 划分表（Phase | 改进点 | 复杂度 | 前置依赖）
   → 定义成功指标

3. 等待用户确认（PO_DONE）
   → 用户可能要求增删改（如"移除P5需求"）
   → 同步更新 .sdd-state.json 和 PRD

4. 用户说"继续" → 进入 BA 阶段产出 Spec（AC 验收标准）
```

## Phase 划分原则

| 优先级 | 原则 | 示例 |
|:------:|------|------|
| 1 | **无依赖先行** | Telemetry 无前置依赖，可放在 Phase 4 或与 P1 并行 |
| 2 | **依赖链** | P8(Delta) 依赖 P4(Spec格式)，P4 依赖 P3(探索模式) |
| 3 | **降复杂度排序** | 简单(⭐⭐) → 中等(⭐⭐⭐) → 复杂(⭐⭐⭐⭐) |
| 4 | **不要过度设计** | 每个 Phase 对应一个明确的改进点，不合并不同 scope 的项 |

## PRD 结构模板

```markdown
# PRD — {Change 名称}

> **Product Requirements Document**
> 变更 ID：{change-id}
> 版本：1.0

## 1. 背景
{调研结论摘要}

## 2. 目标
通过 {N} 个改进点达到 {目标描述}

**不改的底线：** {哪些核心原则不变}

## 3. 改进点定义

### P{N} — {改进点名称}

**问题：** ...
**目标：** ...
**关键思路：** ...
**对比参考：** ...

## 4. Phase 划分
| Phase | 改进点 | 复杂度 | 前置依赖 |
|:-----:|--------|:------:|:--------:|

## 5. 成功指标
```

## 关键陷阱

- **不要跳过 PO 阶段直接产出 Tasks**：用户说"安排一下"期望看到结构化的规划（PRD）
- **Phase 依赖链不是固定的**：用户可能要求调整顺序或移除项
- **复杂度标记要诚实**：⭐⭐ = 约2-4h, ⭐⭐⭐ = 约4-8h, ⭐⭐⭐⭐ = 约8h+
- **不要自动推进到下一 Phase**：PRD 确认后，不要问用户"下一步做哪个"

## 与完整 SDD 流程的关系

```
"安排一下" → PO(PRD) → 用户确认 → BA(Spec) → 用户确认 → Design → Tasks → ...
```

"安排一下"的交付物是**一个结构化的规划文档**，不是完整的实施。规划获得批准后再决定是否进入实施。
