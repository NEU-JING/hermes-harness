# 四层一致性保障的长文档生成机制

> 版本：1.0
> 日期：2026-06-16
> 触发：用户明确纠正「模型输出截断不能靠简单换模型，必须在机制层面解决」
> 状态：✅ 已纳入 SDD 强制执行规范

---

## 问题背景

在 SDD 流程的实战中发现：
- BA 阶段生成 spec.md（~500 行）时，doubao-seed-2.0-pro 模型输出被截断
- Architect 阶段生成 design.md + tasks.md（~1000 行）时，同样遇到输出截断
- 最初的错误做法：简单切换到更大输出的模型（deepseek-v4-pro），但这破坏了 Profile 架构的设计初衷

用户的核心观点：
> 「模型输出长度限制是机制问题，不是模型选择问题。不能靠简单换模型来规避，必须在执行机制层面解决。」

---

## 四层保障机制总览

```
┌─────────────────────────────────────────────────────────────────┐
│ L4: 一致性审计 + 合并去重                                        │
│   术语校验 | 引用修正 | 重复清理 | 层级检查 | 衔接优化          │
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────────┐
│ L3: 递归分块 + 渐进展开                                          │
│   章节 → 小节 → 段落 三级拆分，Agent 自动判断是否需要继续拆     │
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────────┐
│ L2: 上下文锚定                                                  │
│   完整文档地图 + 前一章节最后 3 段 + 后一章节大纲               │
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │
┌─────────────────────────────────────────────────────────────────┐
│ L1: 文档地图（Document Map）                                    │
│   大纲结构 | 全局术语表 | 引用注册表 | 命名约定                  │
└─────────────────────────────────────────────────────────────────┘
```

---

## L1: 文档地图（Document Map）

### 核心思想
先生成一个**小而全**的全局结构摘要（控制在 200 行以内），确保能完整放入任何模型的上下文窗口。所有后续分块生成都必须携带这份文档地图。

### 文档地图内容

```yaml
# document-map.json
outline:                  # 完整章节大纲（带编号）
  - "1. 背景与目标"
  - "2. 用户场景分析"
  - "2.1 场景一：XXX"
  - "2.2 场景二：XXX"
  - "3. 功能范围"
  # ... 更多章节

glossary:                 # 全局术语表（统一定义）
  分块生成: "将大文档拆成多块，分多次写入的机制"
  文档地图: "全局结构与元数据的抽象表示"
  上下文锚定: "每块生成时携带的相邻上下文信息"
  # ... 更多术语

reference_registry:       # 跨章节引用注册表
  R1: "需求1：XXX"
  AC1.1: "验收条件 1.1"
  # ... 更多引用

naming_conventions:       # 命名约定
  模块名: PascalCase
  函数名: snake_case
  变量名: camelCase
  # ... 更多约定
```

### 约束条件
- ✅ 文档地图必须在生成分块内容之前 **100% 完成**
- ✅ 文档地图大小必须控制在 **200 行以内**
- ✅ 任何术语必须先在 glossary 中定义，才能在正文中使用
- ✅ 所有 Agent 生成内容时，**必须携带完整的文档地图**

---

## L2: 上下文锚定（Context Anchoring）

### 核心思想
除了文档地图，每个分块还需要知道「上一块写了什么，下一块要写什么」，确保章节之间衔接自然。

### 每个分块携带的上下文

```
【文档地图】
（完整的 document-map.json 内容，始终携带）

【相邻上下文】
前一章节最后 3 段：
...

后一章节大纲：
...

【当前块任务】
生成第 2.1 节：方案A的详细描述

【过渡语要求】
开头必须用 1-2 句话承接前一章节的结尾
```

### 约束条件
- ✅ 前一章节的最后 **3 段** 必须完整包含
- ✅ 后一章节的完整大纲必须包含
- ✅ 分块开头必须有 **1-2 句过渡语**
- ✅ 总上下文（文档地图 + 相邻上下文 + 当前任务）必须控制在模型窗口的 **50% 以内**

---

## L3: 递归分块 + 渐进展开

### 核心思想
Agent 内部自动判断当前任务的预期输出长度，如果超过安全阈值（200 行），自动拆分成更小的块，不需要人工干预。

### 分块层级

| 层级 | 粒度 | 安全行数 | 携带的额外上下文 |
|------|------|---------|-----------------|
| L1 | 章节级（如「2. 技术方案」） | ≤ 500 行 | 前后章节大纲 |
| L2 | 小节级（如「2.1 方案A」） | ≤ 200 行 | 父章节摘要 + 前后小节 |
| L3 | 段落级（如「2.1.1 原理」） | ≤ 100 行 | 父小节完整内容 + 前后段落开头 |

### 渐进展开流程

```python
def generate_section(section_name, expected_lines):
    if expected_lines <= 200:
        return direct_generate(section_name)
    
    # 自动拆分
    sub_outline = generate_sub_outline(section_name)
    append_to_document_map(sub_outline)
    
    result = []
    for sub_section in sub_outline:
        sub_result = generate_section(sub_section, estimate_lines(sub_section))
        result.append(sub_result)
    
    return join(result)
```

### 最大深度约束
- 正常情况：最大拆分到 **L3（段落级）**
- 如果 L3 还是超长，触发**降级方案**：
  1. 先写要点列表（控制在 10 行内），不写详细说明
  2. 再逐个要点展开（可以突破 L3 深度限制）
  3. 在审计报告中标注「⚠️ 此部分分块深度超过 L3，建议人工审核连贯性」

---

## L4: 一致性审计 + 合并去重

### 核心思想
所有分块生成并合并后，自动执行一轮全面的一致性检查和格式清理。

### 审计检查清单

| 检查项 | 检查方法 | 修复方式 |
|-------|---------|---------|
| **术语一致性** | grep 所有术语，与 glossary 对比 | 列出不一致的术语，给出替换建议 |
| **引用一致性** | 检查所有 `R{N}`/`AC{N}`/`图{N}` 引用是否存在且编号正确 | 列出无效引用和正确的目标编号 |
| **标题层级检查** | 正则匹配所有标题，检查层级跳变（不能从 # 直接跳到 ###） | 自动修正跳变的标题层级 |
| **重复内容清理** | 比对相邻 5 行，相似度 > 80% 则标记 | 自动去重或给出合并建议 |
| **过渡语优化** | 检查每章开头的过渡语是否与前章结尾衔接自然 | 重写建议（避免连续用「上一章我们讨论了...」） |
| **引用编号修正** | 递归拆分过程中新增的子项编号可能与全局编号冲突 | 扫描所有编号引用，重新按文档顺序统一编号 |

### 审计输出格式

```
📋 一致性审计报告
━━━━━━━━━━━━━━━━━━━━

✅ 通过检查项：
- 术语一致性：100% 匹配 (28/28)
- 标题层级：正常
- 引用完整性：全部有效 (12/12)

⚠️ 警告项：
- 第 3.2 节与 3.3 节过渡语重复（相似度 85%）
  建议：将 3.3 节开头改为「在介绍了方案A的基础架构后，我们来看方案B...」
- 第 5.1 节分块深度 L4，建议人工审核

❌ 错误项：
- 无

━━━━━━━━━━━━━━━━━━━━
结论：✅ 通过，建议处理警告项后推进
```

## Agent Skill 集成要求

### ba-agent
- ✅ spec.md 按 Requirement 分块生成
- ✅ 必须先生成文档地图，再写每个 R
- ✅ 每个 R 超过 200 行自动拆分成 AC 级分块

### architect-agent
- ✅ design.md 按「地图→方案→架构→任务」四阶段分块生成
- ✅ 每个阶段超过 300 行自动拆分成小节级分块
- ✅ tasks.md 按 Task 分块（天然适合分块生成）

### 所有 Agent
- ❌ 禁止一次性生成超过 300 行的内容
- ❌ 禁止通过简单切换到大输出模型来规避分块机制
- ✅ 所有 Agent 默认使用四层机制，不需要额外配置

---

## 验收标准（强制执行）

任何 SDD 项目的 BA/Architect 阶段必须满足：

1. ✅ `document-map.json` 文件存在且包含完整的 4 个部分（outline/glossary/reference_registry/naming_conventions）
2. ✅ Agent 执行日志中能看到分块生成的证据（多次 write_file 调用）
3. ✅ 一致性审计报告存在且无 **❌ 错误项**
4. ✅ **模型选择符合原 Profile 配置**（BA 用 doubao-seed-2.0-pro，Architect 用 glm-5.1），没有偷偷切换成大输出模型
5. ✅ 最终产物（spec.md/design.md/tasks.md）完整且章节衔接自然

## 为什么这比简单换模型更好

| 维度 | 换模型 workaround | 四层机制方案 |
|------|-----------------|-------------|
| **Profile 架构完整性** | ❌ 破坏（所有角色都用同一个大输出模型） | ✅ 保持（各角色用各自最适合的模型） |
| **可扩展性** | ❌ 总有更大的文档会触发任何模型的输出限制 | ✅ 无限扩展，理论上可以生成任意长度的文档 |
| **文档质量** | ❌ 长文档上下文会被稀释，前后矛盾概率高 | ✅ 每块都有完整的全局上下文 + 相邻上下文，一致性更好 |
| **可审计性** | ❌ 无法知道截断是因为模型还是内容 | ✅ 每块的生成都有记录，问题可追踪可定位 |
| **可维护性** | ❌ 依赖特定模型的输出能力，模型升级后可能失效 | ✅ 与模型无关，任何模型都可以用 |

## 相关陷阱

### 陷阱 #1：文档地图本身就超 200 行
**现象**：大项目的术语表就有几百个，文档地图本身就超了。

**解决**：
- 术语表只放核心术语（≤ 30 个），其余术语放在附录
- 引用注册表只放跨章节的核心引用（≤ 20 个），局部引用不需要注册
- 命名约定只放最关键的 5-10 条

### 陷阱 #2：分块太多导致上下文切换开销过大
**现象**：100 行拆成 10 块，每块都带 200 行上下文，总 token 消耗是原来的 3 倍。

**解决**：
- 分块粒度平衡：单块 100-200 行是最优区间，不要拆太细
- 相邻上下文动态调整：章节级带前后 3 段，小节级只带前后 1 段

### 陷阱 #3：一致性审计误报
**现象**：审计工具把正常的术语重复使用误判为不一致。

**解决**：
- 审计只做建议，不做强制阻断（只有 error 级才阻断）
- 用户有最终决定权，可以手动跳过审计警告推进流程
